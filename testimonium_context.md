## Runtime architecture

- **Backend:** Node.js ESM, Express 5, Prisma 7/`@prisma/adapter-pg`, PostgreSQL (`pgvector`), Firebase Admin, AWS S3 SDK configured for Cloudflare R2 (public assets and dedicated private identity bucket `R2_IDENTITY_BUCKET_NAME`), Sharp, OCR provider adapters (OCR Space and Stub), `GovernmentIdVerificationService`, `IdempotencyService`, authoritative `SchedulingConfiguration`/`BookingValidator`, centralized conflict helper and domain service (`ScheduleAvailabilityDomainService`), heuristic recommendation algorithm, transactional `EmailOutboxWorker`, Gemini AI integration (`gemini-3.5-flash-lite`, `gemini-embedding-2`), 16 authoritative server-executed live tools, grounded response composer with fact preservation, Caloy runtime configuration with per-request immutable snapshotting, privacy-safe SDK attempt telemetry (`ai_usage_events`), background `knowledgeEmbeddingWorker`, atomic DB-lease coordination (`SystemLeaseService`), and scheduled telemetry retention worker (`CaloyTelemetryRetentionWorker`).
- **Parishioner Web:** React 19, React Router, Firebase client auth, Leaflet, Vite. `VITE_PROVIDER_MODE` supports `api` and `demo`. Features drawer-based Caloy virtual assistant with progressive reveal and sources accordion, parish personnel directory with Mother Parish and clergy cards, and Profile Government ID verification card (`GovernmentIdSection`) with live status and diagnostic error guidance.
- **Admin Portal:** React 19, React Router, Firebase client auth, Leaflet, Vite. `VITE_DATA_PROVIDER` accepts `api`, `demo`, or `hybrid`. Includes verified payment analytics, document requirement assignment matrix, council photo management, User Management with Government ID verification inspection and private card image streaming, full Knowledge Base governance, and the centralized Caloy Control Center (`/caloy` — Overview, Analytics, Knowledge Base, AI Settings, Logs).
- **Parishioner Mobile App:** Expo SDK 57, React Native 0.86, React 19, TypeScript 6, native `@react-native-firebase/auth`, `@react-native-google-signin/google-signin`, TanStack Query, and Expo Router. Modernized 5-tab layout (`(home)`, `(caloy)`, `quick-actions` CenterActionButton, `(notifications)`, `(profile)`), `QuickActionSheet`, interactive native camera scanner with real-time card edge/alignment detection, quality assessment, and perspective normalization (`GovernmentIdCameraScanner`), dedicated Government ID verification wizard (`/profile/id-verification`), dedicated full-screen Caloy chat with session caching (`testimonium_caloy_context_v1:<uid>`), request status timeline with `READY_FOR_SIGNING` mapped to Processing, and deep-link routing. Communicates directly with `/api/v1` (with `npm run dev:mobile` supporting local Android device testing over Cloudflare Quick Tunnel).
- **Storage and Verification:** Document attachments, authorization letters, council officer photos, and receipts are stored in Cloudflare R2 (`R2_BUCKET_NAME`); receipts are asynchronously retrieved, Sharp-optimized in memory, parsed via OCR, cached in process, and flagged for duplicate hashes while remaining subject to mandatory staff verification. Government ID images are strictly isolated in `R2_IDENTITY_BUCKET_NAME` with synchronous OCR verification, Laplacian variance sharpness validation, and private Coordinator streaming routes (`private, no-store`). Confidential files are streamed via authenticated backend download endpoints.

| Role | Boundary |
| --- | --- |
| `PARISHIONER` | Own profile, Government ID verification submission and status, document requests, receipt uploads (with attempt versioning), schedule bookings with preferred priest selection, in-app notifications, Caloy assistant queries, and public discovery feeds across web and mobile. |
| `SECRETARY` | Parish-scoped request processing, document settings/requirement configuration, payment review, verified payment analytics, availability blocks, mass templates, weekday/date rules, daily reports, parish events, council officer photos, and emergency rescheduling. |
| `PRIEST` | Personal commitment calendar management (`/priest/personal-schedules`), parish-scoped operational schedule/event views, read-only document request access within assigned parish (mutations strictly prohibited with 403), read-only scheduling rules and document settings, and liturgical assignment responses. |
| `DIOCESE_COORDINATOR` | Cross-parish administration, directory management (including Mother Parish designation), user management with Government ID verification inspection and private card image streaming, interactive map configuration, parish settings and document requirements governance, weekday/date rules, daily reports, system analytics, verified payment feeds, Caloy Control Center management (`VIEW_CALOY`, `MANAGE_CALOY_SETTINGS`, `VIEW_CALOY_LOGS`, `MANAGE_CALOY_LOGS`, `MANAGE_KNOWLEDGE_BASE`), Knowledge Base governance, and audit log retention. |

Staff tenancy is strictly derived from verified server identity, not client parameters. Parishioner mutations require a completed user profile (full name and contact number) and an effectively verified Government ID (unverified accounts receive `403 IDENTITY_NOT_VERIFIED` on request creation and appointment scheduling).

## Data model and workflows

The Prisma schema defines 34 models and 28 enums across identity, government ID verification, parish and council governance, documents and payments, scheduling and personal calendars, notifications, FAQ, audit, Mass templates, events, reports, transactional email, idempotency, and the governed AI/RAG knowledge source, chunk, chatbot telemetry records, runtime configuration, system leases, and AI usage events.

- **Government ID Verification:** End-to-end automated verification flow for Philippine government-issued card IDs: PhilSys / National ID, Driver's License, UMID, Voter's ID, and Postal ID (passports, student IDs, and company IDs unsupported). Synchronous validation evaluates Sharp Laplacian variance sharpness (>= 15), distinct SHA-256 hashes, concurrent front/back OCR Space processing, card classification regex markers, Levenshtein legal name matching against user profile, and expiration checks. Stored in dedicated private bucket `R2_IDENTITY_BUCKET_NAME`, guarded by `SystemLease` concurrency locking (`GOVERNMENT_ID_VERIFICATION:<userId>`), streamed privately to Diocese Coordinators, and automatically invalidated upon material legal name changes. Verified Government ID status gates sacramental document requests and appointments, and automatically fulfills the canonical `valid_id` requirement.
- **Document Requests:** Draft creation, fee snapshots, supporting file and authorization letter uploads, configurable requirement matrix (parish-specific requirement toggles and pricing validated against 8 canonical requirements, with `valid_id` auto-satisfied by verified Government ID), staff review cycles, internal staff signing stage (`READY_FOR_SIGNING` between `PROCESSING` and `READY_FOR_PICKUP` with active primary priest in-app notification; mapped to Processing for parishioners), Priest parish-scoped read-only access (mutations forbidden), correction requests/resubmissions, authenticated download streaming, payment proof uploads, and immutable history logging.
- **Payments & Analytics:** R2 storage, receipt attempt versioning (`attempt_version`, `is_superseded`) preserving full audit history while enforcing at most one active receipt per transaction, SHA-256 duplicate image detection, OCR reference/amount extraction, staff verification workflows, and paginated verified payment analytics (`GET /analytics/payments/verified`) with Manila timezone boundaries and server-side search.
- **Scheduling:** 16 canonical event types, backend-enforced parish event settings (services, time slots, daily/per-slot capacities), persisted weekday/date rules, availability range checks, dynamic slot calculation, constraint-based recommendation algorithm with heuristic ranking, preferred priest requests (`requested_priest_id`), row-locked booking/configuration writes (requiring completed profile and verified Government ID), reschedule negotiation, emergency rescheduling with version bumping, append-only `ScheduleHistory`, and database-backed idempotency key deduplication.
- **Priest Personal Calendar:** Discrete `priest_personal_schedules` records with interval check constraints (`end_at > start_at`), optimistic versioning, and unified calendar conflict prevention across parish scheduling and personal commitments.
- **Parish Governance:** Parish-level Mother Parish designation (`is_mother_parish`, default `false`) with no parent/child parish hierarchy, strictly enforced at database level via partial unique index `parishes_single_mother_parish_idx` (at most one per diocese), primary and assistant clergy visibility (`assistantPriests` array), Parish Pastoral Council (PPC) and optional Parish Finance Council (PFC) administration with position titles, member sorting, officer photos stored in R2 (`photo_object_key`, `photo_url`), dormant state preservation when PFC is toggled off, optimistic concurrency versioning, and public directory visibility.
- **Caloy AI & Centralized Control Center:** Gemini semantic intent routing, 16 registered authoritative server-executed live tools, grounded response composition with fact preservation, multilingual mirroring, pgvector retrieval (`gemini-embedding-2`), and coordinator Control Center (`/caloy`). Runtime configuration distinguishes a verified empty row, immutable last-known-good degraded operation, and cold fail-closed database failure; environment model values never self-approve outside the deliberate compatibility catalog. Each query uses one immutable snapshot, effective model, trace ID, monotonic 5-28 second root deadline, and shared abort signal across every AI path. Privacy-safe provider attempts use canonical `GENERATE_CONTENT`/`EMBED_CONTENT` telemetry. Automatic retention is limited to 03:00-03:59 Asia/Manila once per day, skips unverified runtime state, and serializes with manual purge through a renewable database-clock lease (`SystemLease`). Conversation Review is excluded.
- **Mobile Integration:** Complete parity with parishioner web capabilities, including camera/gallery receipt capture with HEIC conversion, modernized 5-tab navigation with central `QuickActionSheet`, interactive native camera scanner with real-time card edge/alignment detection (`GovernmentIdCameraScanner`), dedicated Government ID verification wizard (`/profile/id-verification`), dedicated Caloy assistant experience, multi-step wizards, and deep-link routing. Mobile API calls use one monotonic overall deadline across initial Firebase token acquisition, the first HTTP attempt, forced token refresh after 401, and the retry; no phase receives a fresh timeout budget.
- **Transactional Outbox:** Guaranteed document-lifecycle and schedule status email dispatch via PostgreSQL transactional `email_outbox` claimed with `FOR UPDATE SKIP LOCKED`, honoring user-configurable `emailNotificationsEnabled` preferences.

## Contributor guardrails

- Update routes, validation schemas, controllers/services, web providers, mobile services, and documentation in lockstep.
- Create explicit Prisma migrations for schema changes; never use `prisma db push` in production.
- Keep R2 object keys in the database and never expose storage credentials or direct database connections to web or mobile clients.
- Build and verify all clients before handoff (`npm run build:all`, `npm test` across backend and mobile).
