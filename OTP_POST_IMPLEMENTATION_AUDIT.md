### Security and cross-system behavior after correction

- Codes are six-digit strings from crypto.randomInt, preserving leading zeros; OTP and grant comparisons use HMAC-SHA256 and timingSafeEqual. OTP HMACs bind purpose, normalized email, UID and a random per-challenge binding. Reset grants contain 32 random bytes. PostgreSQL stores hashes, never raw codes, passwords or grants.
- OTP and reset-grant lifetimes are ten minutes. Five wrong attempts is terminal. Resends enforce 60 seconds and at most five reserved sends per account/purpose in a rolling 24 hours. Both UID and email participate, so changing email does not reset the account quota. Failed/ambiguous send reservations count conservatively toward the cap.
- Database transactions acquire sorted email/UID advisory locks, including when no challenge exists yet. The default PostgreSQL transaction isolation is used; transactions read the challenge only after obtaining the relevant lock. Real PostgreSQL execution/locking was **not** verified here; the disposable test is available below.
- Auth-specific IP keys normalize IPv6 subnets. Existing IP middleware remains process-local; account send quotas, attempt limits and grant state are persisted and shared across backend instances. No Redis platform or unrelated limiter was introduced.
- Password reset requests acknowledge a request before eligibility/provider work. The response deliberately says **requested**, not **delivered**. Eligible dispatch executes in the backend process. A process restart before dispatch can lose that attempt; the user can request again. No raw OTP is written to an outbox. Delivery failure leaves the reserved code unusable and allows a later fresh request within quotas.
- Firebase and PostgreSQL do **not** form an atomic distributed transaction. A reset first commits its grant claim and operation/password HMAC. APPLYING means the password outcome may be ambiguous; APPLIED means Firebase returned success; COMPLETED records revocation and completion. The two-minute lease prevents simultaneous retry work. Same completed request returns a receipt without changing a password again. A different password cannot reuse that grant.
- If Firebase succeeds and the stage write fails, session revocation is still attempted. Retrying an ambiguous APPLYING operation never calls updatePassword again: it revokes/reconciles and directs the user to sign in or request a fresh code. If revocation fails from APPLIED, a retry resumes revocation without another password update. Explicit Firebase password-policy rejection safely releases the grant for correction. An ambiguous provider timeout cannot be truthfully labelled successful.
- Verification updates use the checked email together with emailVerified in the Firebase update, so a concurrent independent email change cannot cause a different unowned address to be marked verified. The update targets one UID. Database user synchronization also targets that UID only. Firebase Admin supports updating these account fields by UID. [Firebase user management](https://firebase.google.com/docs/auth/admin/manage-users).
- Existing authentication middleware continues verifyIdToken(token, true), checking revoked tokens. The reset explicitly revokes refresh tokens; password changes also invalidate Firebase refresh sessions under Firebase's documented behavior. [Firebase session management](https://firebase.google.com/docs/auth/admin/manage-sessions).
- The new table retains RLS with no public policies and explicit table/sequence privilege revocation for PUBLIC, anon and authenticated. Only the privileged backend connection should access it. These are separate protections: grants control table access and RLS controls row access. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

## D. Remaining limitations

1. Real Gmail delivery, recipient inbox placement, actual email-client CID image rendering, live Firebase password/verification/session operations, production end-to-end behavior and physical Android behavior were not exercised. Browser tests use controlled Firebase/HTTP boundaries and native tests use mocks.
2. The migration and real advisory-lock concurrency/RLS behavior still need the disposable PostgreSQL run. Set OTP_TEST_DATABASE_URL only to an **empty local database named otp_audit_***, then run the opt-in test. It refuses non-loopback hosts, other database names and databases with existing public tables. Use a disposable cluster with a privileged test user; it bootstraps Supabase's anon/authenticated roles if absent and cleans up its OTP objects. Never point it at an application database or live Supabase.
3. An ambiguous Firebase outcome cannot be conclusively reconciled across two independent systems. The implemented safe behavior prevents replay, attempts revocation, and offers sign-in/fresh-code recovery. A later identical request resumes cleanup within the grant lifetime, after the two-minute lease. There is no autonomous cross-system reconciliation worker.
4. Reset dispatch is asynchronous in the backend process to avoid an account-eligibility timing oracle. Restart/interruption before delivery can require another request. The acknowledgement does not claim mail was sent. Failed reservations intentionally consume send budget.
5. No standalone Flash OTP implementation report or GitHub OTP-email reference was present in the supplied attachment or located in the working tree. The attached requirements, actual source, existing client contracts and rendered templates were reviewed directly. No comparison to an unavailable reference is claimed.

No other confirmed feature defect was left as a recommendation instead of a code correction. The limitations above are external validation/configuration boundaries and explicit recovery tradeoffs.
